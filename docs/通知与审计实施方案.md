# 通知与审计实施方案

- 状态：**待评审**
- 日期：2026-09-14
- 关联：需求确认书 §3.5 可维护性·日志与监控、§2.2 审核 / 证书 / 任务下发、§2.3 闯关与技能树；`app/models/notification.py`、`app/schemas/notification.py`、`docs/数据库表字段清单.md` §8、`app/services/attempt.py`、`app/services/skill.py`
- 范围：**站内通知的生成与读取** + **关键操作的审计留痕**。不做实时推送（WebSocket）、不做集中式日志采集（ELK / Loki）、不做监控告警——这三项属于运维侧非功能需求，另案处理。

---

## 0. 结论先行

1. **需求书里没有"通知与审计"这个功能模块。** 功能需求明细（§二）通篇只有一处明确写了"推送"——[§2.2 复审详情页]「复审结果（教师分数与批注）将同步推送至学生端展示」；其余通知需求都隐含在业务描述里（任务下发、AI 评审结果、技能点亮、证书审核）。审计侧的依据是非功能需求 §3.5「日志集中收集与分析」（P1）。**所以埋点范围要以现有代码里真实存在的关键动作为准**，不能照需求书的模块列表抄（§1 逐条列了出处）。
2. **两张表已经在库里**：`notification`、`operation_log`（含索引），`NotificationBizType` 枚举和 `app/schemas/notification.py` 骨架也在。**本期不新增表、不加字段、不需要 Alembic 迁移**，表数仍是 39。
3. **通知和审计是两件事，不要合并成一张表。** 通知面向"接收人"，可已读、会过期清理、给人看；审计面向"操作人"，append-only、不可改、给合规看。同一次操作常常两者都写（教师定稿 → 学生收通知 + 审计留痕），但生命周期和权限完全不同。
4. **通知必须与业务同事务写入**，否则会出现"评审通过了但通知没发"或"通知发了但业务回滚"。审计同理，但审计写失败时**不能把学生的提交也搞失败**——这条要按事件分级（§4.3）。
5. **审计埋在 service 层，不埋 endpoint 层**：关键操作（评审定稿、技能结算、提交）都发生在 `app/services/*`，那里拿不到 `Request`。解决办法是用中间件把 IP / UA / 操作人塞进 `ContextVar`，service 直接取（§4.2）。
6. **不做实时推送。** 前端轮询"未读数 + 列表"即可（建议 30s 一次）。将来要 WebSocket 时，通知表天然就是离线消息队列，不用改表。
7. 工作量约 **4.5 天**（P1~P5）。

## 3. 通知的设计

### 3.1 生成侧：一个薄封装，两种写入口

```python
# app/services/notify.py
async def notify(
    session: AsyncSession,
    *,
    recipient_user_id: int,
    title: str,
    content: str | None = None,
    biz_type: str,
    biz_id: int | None = None,
) -> Notification | None:
    """写一条站内通知（与业务同事务；同 biz_type+biz_id 幂等，重复触发不刷屏）。"""


async def notify_many(
    session: AsyncSession,
    *,
    recipient_user_ids: Sequence[int],
    title: str,
    content: str | None = None,
    biz_type: str,
    biz_id: int | None = None,
) -> int:
    """批量写（任务下发面向一个班，50+ 人一次插入；已存在的跳过）。"""
```

三个刻意的约束：

1. **同事务**：`notify()` 只 `flush` 不 `commit`，事务边界统一由 `get_db` 收口。业务成功 → 通知一定在；业务回滚 → 通知一起没。
2. **幂等**：写之前按 `(recipient_user_id, biz_type, biz_id)` 查一次，已存在就跳过。定稿、重试、批量补发这类场景很容易重复触发，不幂等会让同一个学生收到三条"你的报告通过了"。
3. **文案在调用点给**，不在表里存模板：`title` 是给人看的短句（"实训报告已通过"），`content` 放细节（"《三端稳压管引脚检测》85.5 分，教师批注：……"）。`biz_type + biz_id` 让前端能点进对应详情页，不用解析文案。

### 3.2 触发点埋在哪

埋点位置全部选在 **service 层的关键动作之后**，不放在 endpoint：

| 事件 | 埋点位置 | biz_type | biz_id | 标题 / 内容要点 |
| --- | --- | --- | --- | --- |
| AI 评审出结果 | `ai_review.run_ai_review` 结算后 | `REVIEW_RESULT` | `review_id` | 「AI 评审完成」+ 总分与结论 |
| 学生申请复审 | `attempt.raise_objection` | `REVIEW_RESULT` | `submission_id` | 发给**任课教师**：「有学生申请复审」+ 学生与项目名 |
| 教师复审定稿 | `attempt.finalize_review` | `REVIEW_RESULT` | `review_id` | 「实训报告已复审」+ 教师分数与批注 |
| 关卡通过 / 下一关解锁 | `attempt.submit_attempt` | `STAGE_RESULT` | `attempt_stage_id` | 「关卡通过，下一关已解锁」 |
| 技能点亮 / 升级 / 满级 | `skill.recalculate_student_skills` 前后状态对比 | `POINT` | `student_skill_id` | 「技能已激活：图像基础」 |
| 证书审核 / 发放 / 作废 | 证书模块（待建） | `CERT` | `student_certificate_id` | 「证书已发放：工业视觉检测（初级）」 |
| 任务发布 / 撤回 | 任务模块（待建） | `TASK_PUBLISH` | `task_id` | 「新任务：7 日内完成进阶实训」 |

技能那条要特别说一下：`recalculate_student_skills` 是"重算"，每次项目完成都会跑一遍全量技能，**不能按"重算了"发通知**，必须**比对状态变化**（`LOCKED → ACTIVATED → MASTERED`），只对真正变化的节点发。否则学生会收到一堆重复的"技能已激活"。

### 3.3 读取侧

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/notifications` | 我的通知分页，支持 `unread_only=true`、按 `biz_type` 过滤 |
| GET | `/api/notifications/unread-count` | 未读数（前端轮询这个，30s 一次） |
| PATCH | `/api/notifications/{id}/read` | 标记单条已读 |
| POST | `/api/notifications/read-all` | 全部标记已读（可带 `biz_type`） |

几个细节：

- **只能读自己的**：列表强制按 `recipient_user_id = 当前用户` 过滤，读别人的通知一律 404（不泄露存在性）。
- **已读是时间戳不是状态**：`read_at` 为空即未读，表结构已定，不引入 `status` 字段。
- **排序用 `id DESC`**：`id` 自增、近似时间序；现有索引 `(recipient_user_id, read_at)` 适合"我的未读"筛选。若按 `created_at DESC` 排序则要再加索引（一次迁移），**本期不值得**。
- **不提供删除接口**：需求书没提，表也没有软删字段；清理交给保留期（§3.4）。

### 3.4 保留与清理

通知是"看过就没用"的数据，但比问答历史活得久一点，建议 **30 天**（可配 `notification.rules.retention_days`）。

照搬问答那套两层做法：

- **查询层**：列表与未读数都带 `created_at >= now() - 30d`，清理任务挂了也不影响学生看到的东西；
- **清理层**：`scripts/prune_notifications.py`（复用 `qa.prune_history` 的写法），挂宿主 cron 每天跑一次，按 `created_at < cutoff` 物理删除。

容量上完全不用操心：52 名学生 × 每人每学期约 20 条通知 ≈ 1000 行/学期，30 天滚动窗口下常驻只有几百行。

## 4. 审计的设计

### 4.1 写什么

审计只记**不可抵赖的关键动作**，不记读操作、不记学生的高频操作（问答、保存作答草稿）。判断标准：**这个动作事后被质疑时，需要能拿出"谁、什么时候、对什么、改成了什么"**。

| 模块 `module` | 动作 `action` | 触发点 | 目标 `target_type/id` | `detail_json` 记什么 |
| --- | --- | --- | --- | --- |
| `REVIEW` | `AI_REVIEW` | `ai_review.run_ai_review` | `submission` / `review` | 总分、结论、用了哪份评分标准（`criteria_doc_ids`）、降级 warnings |
| `REVIEW` | `FINALIZE` | `attempt.finalize_review` | `review` | 教师 ID、改动前后的分数与批注、结论 |
| `REVIEW` | `OBJECTION` | `attempt.raise_objection` | `submission` | 学生、异议理由 |
| `ATTEMPT` | `WITHDRAW` | `attempt.withdraw_submission` | `submission` | 撤回前后状态 |
| `PROJECT` | `PUBLISH` / `OFF_SHELF` | `projects.update_project`（`status` 变化） | `project` | 前后状态、关卡与权重快照 |
| `CERT` | `ISSUE` / `REVOKE` / `REISSUE` | 证书模块（待建） | `certificate` | 证书编号、岗位、原因 |
| `ACCOUNT` | `CREATE` / `DISABLE` / `RESET_PASSWORD` | `accounts` 相关接口 | `user` | 账号、角色变化（**不记密码明文**） |
| `PERMISSION` | `SET_ROLES` / `SET_PERMISSIONS` | `accounts` 角色权限接口 | `user` / `role` | 变更前后集合 |
| `CONFIG` | `UPDATE` | `accounts` 系统配置接口 | `system_config` | **脱敏后的**前后值（api key 只留掩码） |
| `KNOWLEDGE` | `UPLOAD` / `REINDEX` / `DELETE` | `knowledge_ingest.*` | `knowledge_doc` | 文档标题、切片数、用途 |

> 系统配置那一条要特别注意：`ai.llm.api_key` 就落在 `system_config` 里，`detail_json` 存前后快照时必须走 `app/core/secrets.py` 的掩码，**绝不能把明文 key 写进审计表**。

### 4.2 怎么拿到操作人和请求信息

关键动作发生在 service 层，那里没有 `Request`。方案：加一个中间件把请求元信息放进 `ContextVar`，`audit()` 直接读。

```python
# app/services/audit.py
_request_meta: ContextVar[dict[str, Any]] = ContextVar("request_meta", default={})


async def audit(
    session: AsyncSession,
    *,
    module: str,
    action: str,
    operator_id: int | None = None,
    target_type: str | None = None,
    target_id: int | None = None,
    detail: dict[str, Any] | None = None,
) -> None:
    """写一条审计日志（append-only）。operator / ip / ua 缺省从 ContextVar 取。"""
```

中间件（`app/main.py` 注册）负责把 `ip`、`user_agent` 塞进 `ContextVar`；`operator_id` 一期由接口显式传（同问答的 `student_id` 做法），SSO / RBAC 落地后由 `current_user` 依赖统一注入——**只改一处**。

### 4.3 写失败怎么办

这是唯一需要权衡的地方。两种策略，按事件分级：

| 级别 | 事件 | 策略 |
| --- | --- | --- |
| 强一致 | 发布 / 下架、评审定稿、证书发放 / 作废、角色权限变更、系统配置修改 | 审计与业务**同事务**：审计写不进去就整体回滚，宁可操作失败也不能没有留痕 |
| 最终一致 | AI 评审、知识文档入库 | 审计失败只记应用日志、不影响业务；这些动作的业务表本身就是二次证据（`review_record.raw_json`、`knowledge_doc` 状态） |

理由：强一致那批是"人对人"的操作（教师改分、发证、改权限），出问题要追责；最终一致那批要么是机器动作、要么业务表里已经留了痕。

### 4.4 查询

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/operation-logs` | 审计日志分页，支持按 `module` / `action` / `operator_id` / `target_type` / `target_id` / 时间范围过滤 |
| GET | `/api/operation-logs/{id}` | 单条详情（完整 `detail_json`） |

权限：**只有教师 / 管理员能查**，学生无权限（能查自己的操作记录等于告诉他审计口径）。审计日志**没有写接口、没有改接口、没有删接口**——`operation_log` 是 append-only，只由 `audit()` 在业务链路里写。

防篡改的边界要说清楚：接口层做到了"不可改"，但直连 SQLite 文件仍然能改。真要做到数据库层不可篡改需要触发器或外部日志系统（§10 风险 4），本方案不做。

### 4.5 保留策略

审计日志不参与日常清理（追责窗口越长越好），建议保留 **12 个月**，之后归档到 MinIO 再从库里删。也写一个带 `--dry-run` 的脚本，但**默认不挂 cron**，由管理员按需要手动跑。

## 6. 配置项（`system_config`）

新增两个键（KV 表，**加键不需要迁移**），同步 `settings_store.DEFAULTS` 与 `app/db/seed.py`：

```json
{
  "notification.rules": {"enabled": true, "retention_days": 30},
  "audit.rules": {
    "enabled": true,
    "retention_days": 365,
    "mask_fields": ["api_key", "password", "password_hash", "secret"],
    "record_request_body": false
  }
}
```

`enabled=false` 用来应急关停（比如通知文案出问题要止血），不用发版；`record_request_body` 默认关，避免把上传文件、作答正文这类大字段写进审计表。

- [ ] **复审定稿**：教师定稿后，学生收到 1 条 `REVIEW_RESULT` 通知，`biz_id` 指向该 `review_id`，点进去能对上分数与批注。

- [ ] **幂等**：同一次定稿重复触发（重试 / 二次调用）不会让学生收到第二条。
- [ ] **技能点亮**：项目完成后，只有状态真的变化的技能节点发通知，重算不重复发。
- [ ] **同事务**：业务抛异常时通知不落库（用一条会失败的业务链路验证）。
- [ ] **越权**：用别人的 `user_id` 读通知 → 404；学生调 `/api/operation-logs` → 无权限。

## 10. 风险与待确认

1. **任务下发（`TASK_PUBLISH`）没有业务表。** 需求书 [§2.2 任务下发] 要"目标班级 / 分组 / 岗位 / 项目层级 + 即时或定时发布"，目前库里只有 `training_project.status`，没有任务实体。这块要单独出方案（含**定时发布**需要的调度器），本方案只预留 `biz_type` 与文案位。
2. **证书模块没有接口。** `student_certificate` 表建好了，但没有审核 / 发放 / 作废接口，`CERT` 类通知与审计要等它落地。
3. **实时性只有轮询。** 前端 30s 轮询未读数是当前唯一手段；如果需要"立刻弹出"，要上 WebSocket，那是独立的一期。**需求书里"推送至学生端展示"指的是结果要在学生端能看到，轮询即可满足，不必按实时推送理解。**
4. **审计的"不可篡改"只到接口层。** 直连 SQLite 文件仍可改。要真不可篡改需要 DB 触发器或把审计同步到外部日志系统（需求书 §3.5 的"日志集中收集"其实是这个方向的更大命题）。
5. **教师端"预警项目"不进通知。** 需求书 [§2.2 数据总览] 的预警是页面上的列表，做成站内通知会让教师端定期收到一堆噪声。建议只做页面；若要做，走"每日汇总一条"而不是每项目一条。
6. **通知文案的维护方式。** 本方案把文案写在调用点（代码里），改文案要发版。若要教师可改，需要一张模板表（新增表 → 表数 40，要动断言与迁移）。建议先用 `system_config` 存少量可覆盖文案，真需要模板化再评估。
7. **保留期是产品规则。** 通知 30 天、审计 12 个月都是本方案的建议值，需求书没有依据，需要校方 / 教师确认；确认后写进界面提示（通知列表上标明"仅保留最近 30 天"）。
