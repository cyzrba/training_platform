## 0. 通用约定

| 项 | 说明 |
| --- | --- |
| 前缀 | 所有接口都在 `/api` 下 |
| 响应体 | 统一为 `{"code": 200, "data": <业务数据>, "msg": "ok"}`；失败时 `code=422`、`msg` 是给人看的提示、`data` 是明细（如导入的逐行错误） |
| 响应体例外 | 只有三个接口**不带信封**：`GET /api/classes/students/import-template`、`GET /api/file-assets/{id}/download` 返回文件流；`POST /api/qa/sessions/{id}/ask` 默认返回 SSE（`stream=false` 时才带信封） |
| HTTP 状态码 | 不要只看状态码：业务失败时状态码**可能仍是 200**，判定看 body 里的 `code`（新建接口成功返回 201） |
| 分页 | `?page=1&page_size=20`；返回 `{items, total, page, page_size, pages}`，`page_size` 上限 200 |
| 时间 | 本地时间、ISO 8601 无时区后缀，如 `2026-09-15T21:53:00` |
| 数值型字段 | 权重、分数、进度、`pass_score` 等 Decimal 字段在 JSON 里是**字符串**（如 `"88.00"`、`"100.0000000000"`），前端要 `parseFloat` 后再算 |
| 鉴权 | **当前没有鉴权层**，接口靠调用方显式传 `teacher_id` / `student_id` / `class_id`；接入登录后这些 ID 应从登录态取，不要信前端传来的值 |
| 删除 | 主数据表都是**软删**（置 `deleted_at`），记录仍可追溯 |

调用示例统一用 `curl`，`BASE=http://127.0.0.1:8000/api`；交互式文档在 `GET /docs`，原始规格在 `GET /openapi.json`。

字段（新建 `SysUserCreate`）：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |

返回体（`SysUserRead`）= 上面全部字段 + `id` / `created_at` / `updated_at` / `deleted_at`（**不含任何密码字段**）：

```json
{
  "code": 200,
  "msg": "ok",
  "data": {
    "id": 2,
    "user_no": "S001",
    "real_name": "张三",
    "user_type": "STUDENT",
    "ext_uid": null,
    "major_name": "人工智能技术应用",
    "avatar_url": null,
    "phone": null,
    "email": null,
    "status": "ACTIVE",
    "last_login_at": null,
    "remark": null,
    "created_at": "2026-09-16T10:00:00",
    "updated_at": "2026-09-16T10:00:00",
    "deleted_at": null
  }
}
```

密码相关：

```bash
# 重置成指定的新密码
curl -X POST $BASE/users/2/password/reset -H 'Content-Type: application/json' -d '{"new_password":"Aq123456"}'
# 重置成系统默认密码（body 传 {} 或不传 new_password）
curl -X POST $BASE/users/2/password/reset -H 'Content-Type: application/json' -d '{}'
# 批量重置（返回实际被重置的账号数）
curl -X POST $BASE/users/password/reset-batch -H 'Content-Type: application/json' -d '{"user_ids":[2,3,4]}'
```

```json
{"code": 200, "msg": "ok", "data": {"updated": 2, "user_ids": [1, 2]}}
```

要点与坑：

1. **密码只存哈希**，任何接口都不会返回密码；`new_password` 留空 = 重置为 `settings.default_password`（默认 `123456`）。
2. 新建用户时 `user_no` 重复 → `code=422`、`msg="学号/工号 S001 已存在"`。
3. 批量重置时**传进来的 ID 里不存在的会被静默跳过**（返回的 `updated` 小于列表长度是正常的）；**一个都没匹配到时**才报 `code=422`、`msg="没有匹配到可重置的用户"`。
4. 设置用户角色是**覆盖式**：`{"role_ids":[1,2]}` 会先把原有角色全清掉再写这两条；`role_ids` 里有不存在的角色 → `msg="角色 9 不存在"`。
5. `DELETE /users/{id}` 是软删，学生账号软删后在花名册里会显示为异常，请优先用「学生离班」（§4.7）而不是删账号。

注意：`group_count` 只是列表上显示的数字，**分组要另外调接口建**（见 §4.6.1），否则学生分不进去。

### 4.3 批量导入学生（Excel）

`POST /api/classes/{class_id}/students/import` → **200**（`multipart/form-data`）

| 参数 | 位置 | 类型 | 说明 |
| --- | --- | --- | --- |
| class_id | path | int | 目标班级 |
| file | form-data | xlsx 文件 | 填写好的学生名单 |
| dry_run | form-data | bool | `true` = 只校验不落库（默认 false） |
| reuse_existing | form-data | bool | `true` = **学号已存在时复用账号并加入本班**（换老师 / 转班场景，见 §4.3.2）；`false`（默认）= 已存在的学号按"整批失败"处理 |

先下载模板：`GET /api/classes/students/import-template`

模板列（第一行必须是这些表头）：

| 专业 | 否 | `major_name` |
| 手机号 | 否 | `phone` |
| 邮箱 | 否 | `email` |
| 分组序号 | 否 | 兼容历史模板的可选列：**该分组已存在**就顺手分进去；还没建就忽略，并在 `ignored_group_hints` 里计数（不会整批失败） |

```bash

curl -X POST $BASE/classes/1/students/import \
  -F 'file=@学生名单.xlsx' \
  -F 'dry_run=true'

# 校验通过后再真正导入
curl -X POST $BASE/classes/1/students/import -F 'file=@学生名单.xlsx'
```

```json

  "msg": "ok",
  "data": {

    "class_id": 1,
    "total": 42,
    "created_users": 42,
    "reused_users": 0,
    "created_class_students": 42,
    "assigned_groups": 0,
    "ignored_group_hints": 0
  }

```

**校验是整批的**：文件里学号重复、姓名缺失、以及（默认模式下）学号已存在 —— 任意一处命中就整批拒绝，`data` 是逐行原因，一行都不会落库：

```json
{
  "code": 422,
  "msg": "名单校验未通过，共 2 处问题，已全部撤回未导入",
  "data": [
    {"row": 4, "user_no": "2026004", "reason": "文件内学号重复"},

```

**"学号已存在"默认算失败，但可以关掉**：默认模式是"建新号并拉进班"，名单里出现库里已有的学号会被整批打回（`reason="学号 2026001 已存在，未导入"`），此时 `created_users == total`、`reused_users = 0`。换老师 / 转班这类"账号已经有了、只是要重新入班"的场景，带 `reuse_existing=true`：已存在的学号不再报错，账号原样复用、只补一条在班记录，`reused_users` 就是复用的人数（见 §4.3.2）。只补录一两个人也可以用下面 §4.3.1 的单个加人接口。

其他要点：新建账号用默认密码（`settings.default_password`，默认 123456，只存哈希）；`created_class_students` 是新建的在班记录数；`dry_run=true` 时账号、在班记录、分组一条都不写。

#### 4.3.1 补充：单个加人（账号已存在则复用）

| real_name | string(50) | 否 | 姓名；账号不存在时必填 |
| major_name / phone / email | string | 否 | 仅在建号时写入 |
| group_no | int(1~99) | 否 | 入班的同时分到第几组（分组必须已建，否则报错） |

#### 4.3.2 接管旧班 / 转班：学生的进度能不能保留？

**能，而且是完整保留**——完成状态、最高分、历次提交与评审、技能进度，全部挂在"学生账号 × 实训项目"上，跟班级、任务、老师都没有绑定关系。甲老师离职、乙老师接手同一个岗位的学生，只要满足下面三条，学生一进新班就看到自己之前的成绩。

| 做法 | 学生的进度 |
| --- | --- |
| **同一账号**（同学号复用）+ **同一个实训项目** | ✅ 完整保留：`completed_at`、`best_score`、提交/评审历史、技能进度都在；新任务一发布，教师看板里这些学生直接就是"已完成" |
| 同一账号，但把项目**复制**成新项目（新的 `training_project.id`） | ❌ 不跟过来：完成记录按 `project_id` 关联，学生要在新项目上重新闯关（老项目上的成绩还在库里，只是这次任务不认） |
| **换了账号**（学号改了、重新建号） | ❌ 不跟过来：进度跟着账号走 |

操作三步（对应甲→乙的交接）：

```bash
# 1) 乙老师建新班
NEW=$(curl -s -X POST $BASE/classes -H 'Content-Type: application/json' \
  -d '{"class_name":"人工智能2402班","head_teacher_id":7}' | jq -r .data.id)

# 2) 用原来那份名单导入，带 reuse_existing=true：
#    学号已存在 → 复用账号 + 在本班建一条在班记录（reused_users 会告诉老师复用了几个人）
curl -s -X POST $BASE/classes/$NEW/students/import \
  -F 'file=@原班学生名单.xlsx' -F 'reuse_existing=true' | jq

# 3) 发任务时**复用原来那个已发布的实训项目**（不要复制成新项目）
curl -s -X POST $BASE/publish-tasks -H 'Content-Type: application/json' \
  -d "{\"title\":\"基础实训（乙老师）\",\"project_ids\":[<原项目 id>],
       \"targets\":[{\"class_id\":$NEW,\"target_type\":\"CLASS\"}],\"publish_mode\":\"IMMEDIATE\"}" | jq
```

三个要提前想清楚的点：

1. **新任务里这些学生一开始就是"已完成"**：完成是按"学生 × 项目"记的，不按班级 / 任务重算。所以乙老师的新任务看板可能一发布就显示 100%，这通常正是要的效果（接着往下教），但**如果教学上要求新班重做一遍，目前没有"按班重置完成状态"的功能**，需要另外评估。
2. **换班不影响项目可见性与技能进度**：技能分母是"全部已发布项目"，与班级 / 任务无关，所以旧班删除、学生离班期间进度不变（只是不再带必修标记）；项目本身 `PUBLISHED` 就照旧能看能做。**完成状态、分数、提交历史都在库里**。
3. **必修标记跟着班级走**：交接时按"先建新班 + `reuse_existing=true` 把学生加进去 + 再发同样的任务，最后处理旧班"的顺序做，学生全程都有必修项，不会出现空窗期。

## 5. 教师工作台：任教班级总览

`GET /api/teachers/{teacher_id}/classes`

一次拿到：**我任教的班级 → 每个班的学生总数 → 分组明细（每组有哪些学生，带 id 和名字）→ 每个发布任务的完成进度 → 平均完成率**。教师工作台首页可以直接用这一个接口渲染。

### 5.1 参数

| 参数 | 位置 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| teacher_id | path | int | — | 教师用户 ID（`sys_user.id`，`user_type` 为 `TEACHER` 或 `ADMIN`） |
| with_task_students | query | bool | true | `true` 时每个任务带逐学生明细；`false` 只给汇总数字（班级多、人多的场景省流量） |

```bash
curl "$BASE/teachers/2/classes"
curl "$BASE/teachers/2/classes?with_task_students=false"
```

### 5.2 响应结构

顶层：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| teacher_id / teacher_name | int / string | 教师 ID 与姓名 |
| class_count | int | 任教班级数 |
| student_count | int | 所有任教班级的在班学生总数（跨班不去重） |
| task_count | int | 命中的任务数（同一任务发给多个班只算一次，含待发布 / 已撤回） |
| average_completion_rate | float | 各班级平均完成率的平均值；没有任务时为 0 |
| generated_at | datetime | 统计时间 |
| classes | array | 班级列表，见下 |

班级对象 `classes[]`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| class_id / class_name | int / string | 班级 ID / 名称 |
| grade_year / status / remark | int / string / string | 年级、`ACTIVE`/`ARCHIVED`、备注 |
| student_count | int | 在班学生总数 |
| group_count | int | 分组数 |
| ungrouped_count | int | **还没分组的学生数** |
| groups[] | array | 每个分组：`group_id` / `group_no` / `group_name` / `member_count` / `members[]` |
| groups[].members[] | array | 组内学生：`class_student_id`（**重新分组时用这个**）、`student_id`、`user_no`、`real_name`、`major_name` |
| ungrouped_students[] | array | 未分组学生（结构同 members），教师可以直接拖进某个组 |
| task_count | int | 命中该班的任务数（含待发布 / 已撤回） |
| average_completion_rate | float | 该班**已发布**任务完成率的平均值 |
| tasks[] | array | 该班的任务进度，见下 |

任务对象 `classes[].tasks[]`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| task_id / title / description | int / string / string | 任务 ID、名称、说明 |
| status | string | `PENDING` 待发布 / `PUBLISHED` 已发布 / `CANCELLED` 已撤回 |
| effective | bool | 是否已生效（= `status == "PUBLISHED"`，学生此刻能看到） |
| publish_mode / published_at / scheduled_at / deadline_at | string / datetime | 发布方式与三个时间点 |
| project_count / project_names | int / string[] | 任务包含的项目数 / 名称 |
| student_count | int | **该任务在本班覆盖的学生数**（全班目标 = 全班；分组目标 = 该组成员数） |
| total_count | int | 应完成的对数 = `student_count × project_count` |
| completed_count | int | 已完成的对数 |
| in_progress_count | int | 已开始但未完成的对数 |
| not_started_count | int | 还没开始的对数 |
| completion_rate | float | `completed_count ÷ total_count × 100`，保留两位小数 |
| students[] | array | 逐学生明细（`with_task_students=false` 时为 `[]`）：`student_id` / `user_no` / `real_name` / `class_student_id` / `group_id` / `group_name` / `completed_count` / `total_count` / `completion_rate` / `status`（`COMPLETED` 全部完成 / `IN_PROGRESS` 进行中 / `NOT_STARTED` 未开始） |

### 5.3 统计口径（重要）

1. **任教班级** = `class_info.head_teacher_id` 指向该教师、且未软删的班级；归档班也会返回（带 `status`），前端自行过滤。
2. **任务命中该班** = 任务的目标里有「全班目标」或「该班某个分组目标」。因此同一个任务发给多个班时，会在每个班里各出现一次（`task_id` 相同，`student_count` 各自算各自的）。
3. **完成 = `student_project.completed_at` 有值**（评审通过并达到及格线），与技能进度的"完成"同源；正在重新挑战、或只提交未评审的都不算完成，计进 `in_progress_count`。
4. **未生效的任务**（`PENDING` / `CANCELLED`）也会列出并统计，因为统计的是"任务里那些项目的实际完成情况"；判断是否该展示进度请看 `effective` 字段。**只有 `PUBLISHED` 任务的完成率进平均完成率**。
5. **平均完成率是算术平均**：班级 = 该班已发布任务完成率的平均；顶层 = 各班级平均完成率的平均（不是"总完成对数 ÷ 总应完成对数"的加权值，前端若要加权口径可用 `completed_count` / `total_count` 自己算）。
6. 分组目标是**按当前分组**实时算的：教师把学生调走，下一次查询的覆盖人数与完成率立刻跟着变。

### 6.2 技能树与技能节点

技能树是**四大体系**（光学成像系 / 传统算法系 / 深度学习系 / 系统部署系），技能节点是最小能力单元。

**技能进度口径**（同样写在 `app/services/skill.py` 顶部）：

1. `progress = 完成项目数 ÷ 关联项目总数 × 100`；
2. **关联项目**（分母）＝ `project_skill` 关联到该节点、**且已经发任务给这名学生**、且项目仍是 `PUBLISHED` 的项目 —— 没发给他的项目不进分母；
3. 状态派生：0 → `LOCKED`；0 < progress < 100 → `ACTIVATED`；100 → `MASTERED`（首次激活 / 精通会写 `activated_at` / `mastered_at`）；
4. 自动重算的四个时机：**评审定稿通过**、**发布 / 撤回任务**、**入班 / 换组 / 离班**、**教师手工调整或手动重算**。

### 6.7 岗位与技能常见坑

1. **技能节点名称是全局唯一**，不是"树内唯一"；不同树用同名技能点会冲突（编码字段已去掉，名字即唯一标识）。
2. **改了岗位技能关联，不会回溯重算历史进度**：分子分母都是"实时算"的，关联一变，下一次查询结果就变；要立刻刷新可以调 `POST /api/students/{id}/skills/recalculate`。
3. **`is_primary` 只有一个**：批量设主岗位时后端会自动清掉旧的，不需要前端先取消。
4. **`pass_score` 直接决定项目能不能算完成**：评审定稿时按项目层级取，没配成长规则或规则 `enabled=false` 时兜底 60 分。
5. **三个成长视图接口都只读、都可匿名调**，上鉴权后要限制"只能看自己的"。

## 7. 实训项目：模块库 / 项目 / 关卡组成 / 附件 / 技能

对应实现：`app/api/endpoints/projects.py`、`app/services/project.py`。

### 7.1 先搞清三个概念

| 概念 | 表 | 说明 |
| --- | --- | --- |
| 模块库条目（关卡模板） | `project_stage_template` | 关卡的**唯一来源**：名称（唯一）、默认权重 / 默认要求 / 默认验收标准。全局共用，不区分岗位与项目 |
| 实训项目 | `training_project` | 一次实训（如「缺陷检测实训」），绑定岗位与层级（`BASIC` / `ADVANCED` / `EXPANDED`）。项目本身是空壳，关卡要一个个从模块库挑进来 |
| 项目关卡组成 | `project_module` | 项目里选中的关卡 = 模板 + 项目内顺序 + 权重 / 必填 / 要求 / 验收标准的**覆盖值**。不能在项目里现场造关卡，要新关卡先去模块库建 |

两个容易混的「发布」：

1. **项目发布**（`PATCH /projects/{id}` 把 `status` 改成 `PUBLISHED`）= 这门实训**编辑完成、可以被任务引用**。发布前校验：至少 1 个关卡，且关卡权重合计**必须等于 100**。
2. **任务发布**（§8）= 把项目**发给具体班级 / 分组**，学生这才看得到。

所以一条完整链路是：模块库建关卡 → 建项目 → 挑关卡并配权重 → 项目置 `PUBLISHED` → 发任务 → 学生在「我的任务」里开始闯关。

项目状态机：`DRAFT` 草稿 → `PUBLISHED` 已发布（可被任务引用）→ `OFF_SHELF` 已下架。**判断学生能不能做，只看有没有生效的发布任务（§8），不看项目状态本身**。

### 7.2 模块库（关卡模板）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/stage-templates` | 分页列表（`page` / `page_size` / `keyword` 按名称模糊搜） |
| POST | `/api/stage-templates` | 新增条目 → **201** |
| GET | `/api/stage-templates/{template_id}` | 详情（多一个 `used_by_projects`：被几个项目选中） |

| DELETE | `/api/stage-templates/{template_id}` | 软删（被项目选中过时不允许删） |

**权重 / 分值等 Decimal 字段在 JSON 里是字符串**（示例写作 `"20.00"`，SQLite 下会看到 `"20.0000000000"`），前端不要当数字直接用，`parseFloat` 之后再用。

系统初始化时（`app/db/seed.py`）会预置需求确认书里的七大标准模块，权重合计正好 100：

| 模块名称 | 默认权重 |
| --- | --- |
| 需求分析 | 10 |
| 方案设计 | 15 |
| 数据处理 | 15 |
| 模型训练 | 20 |
| 模型优化 | 15 |
| 模型测试 | 15 |
| 实训报告上传 | 10 |

也就是说，一个「七大模块全上、不改权重」的项目天然就是 100 分，可以直接发布。

两个坑：

1. **删掉的同名模块还能再建，且会"复活"旧记录**：软删一个模块后，用同一个 `stage_name` 再新增，接口会**恢复原来那条记录并用新内容覆盖**——这时 HTTP 状态码是 **200 而不是 201**，返回的 `id` 还是老的。前端按 body 里的 `code` 判定成功即可。
2. **被项目选中过就删不掉**：返回 `code=422`、`msg="模块「模型训练」已被 1 个项目选中，先从这些项目里移除再删除"`。先在各项目的关卡列表里移除，再删模块库。

### 7.5 项目附件（报告模板 / 数据文件 / 评分标准）

附件分两步：文件先进**文件台账**，再挂到项目；也可以一步到位。`file_kind` 只认 5 个值：`REPORT_TEMPLATE` 报告模板 / `DATASET` 数据文件 / `GUIDE` 说明文档 / `SCORING_CRITERIA` 评分标准 / `OTHER` 其它。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/projects/{project_id}/files?file_kind=DATASET` | 附件列表（`file_kind` 可选） |
| POST | `/api/projects/{project_id}/files` | 挂一个**已经上传**的文件 → **201** |
| POST | `/api/projects/{project_id}/files/upload` | 上传 + 挂载，一步到位 → **201** |
| PATCH | `/api/projects/{project_id}/files/{project_file_id}` | 改名 / 换用途 / 排序 / 备注 |
| DELETE | `/api/projects/{project_id}/files/{project_file_id}` | 解除关联（**文件台账与磁盘文件都保留**） |

一步到位上传（推荐，`multipart/form-data`）：

```bash

  -F 'file=@实验报告模板.docx' \
```

两段式（先传台账再挂）：

```bash
# 1) 上传到文件台账（biz_type 建议与 file_kind 一致，便于台账检索）
ASSET=$(curl -s -X POST $BASE/file-assets/upload -F 'file=@数据集.zip' \
  -F 'biz_type=DATASET' -F 'uploader_id=2' | jq -r .data.id)

# 2) 挂到项目
curl -s -X POST $BASE/projects/1/files -H 'Content-Type: application/json' \
  -d "{\"file_asset_id\":$ASSET,\"file_kind\":\"DATASET\",\"title\":\"训练数据集\"}" | jq
```

要点与坑：

1. `download_url` 是**相对路径**；下载接口 `GET /api/file-assets/{asset_id}/download` 返回**文件流**（不包统一响应体），中文文件名按 RFC 5987 编码。
2. **同一个文件在同一个项目里只能挂一次**：重复挂 → `code=422`、`msg="文件「数据集.zip」已经挂在这个项目上了"`；文件 ID 不存在 → `msg="文件 999 不存在，请先上传"`。
3. `file_kind` 拼错会直接被打回：`msg="未知的附件用途 NOT_A_KIND，可选：REPORT_TEMPLATE / DATASET / GUIDE / SCORING_CRITERIA / OTHER"`。
4. **`SCORING_CRITERIA`（评分标准）是特例**：上传即解析切片入库（知识文档类型 `EVAL_CRITERIA`），响应里多出 `knowledge_doc_id` / `knowledge_status` / `chunk_count` / `knowledge_error` 四个字段；AI 评审（`POST /api/submissions/{id}/ai-review`）靠 RAG 召回它来打分，同一文件重复挂载不会重复入库。
5. 解除关联（`DELETE`）**不会删文件**，文件仍在文件台账里，可以挂到别的项目。

### 7.7 实训项目常见坑

1. **改模块库会影响所有引用它的项目**：模板的权重 / 要求 / 验收标准只是"默认值"，已经加进项目的关卡有自己的覆盖值；但 `stage_name` 是**实时读模板**的，改模板名，所有项目的关卡名一起变。
2. **项目详情才是关卡的真实来源**：列表接口不返回关卡，做「发布前检查」请取详情看 `weight_total` 是不是 100。
3. **项目附件 ≠ 关卡附件**：项目附件（报告模板、数据集）是给整个项目用的；学生每个关卡的作答附件走 `POST /api/attempts/{attempt_id}/stages/{stage_id}/files/{file_asset_id}`（闯关评审域，另见 `app/api/endpoints/attempts.py`）。
4. **删关卡会自动补位**：移除第 3 个关卡后，原来的第 4 个变成第 3 个，`module_id` 不变、`stage_no` 变，前端不要拿 `stage_no` 当稳定标识。
5. **改 `stage_no` 要避让**：手动 `PATCH` 成已占用的序号会被拒，跨位置调整请直接用 `/modules/order`。

## 8. 任务下发：把项目发给班级 / 分组

对应实现：`app/api/endpoints/publish.py`、`app/services/publish.py`。

### 8.1 任务状态与两个"发布"的区别

| 状态 | 含义 | 目标学生 |
| --- | --- | --- |
| `PENDING` | 待发布（含已排期的定时任务） | 任务列表里看不到，项目也还没被点名 |
| `PUBLISHED` | 已发布 | 任务列表里能看到，任务里的项目标成**必修**（`is_required=true`） |
| `CANCELLED` | 已撤回 | 必修标记消失（已产生的闯关记录保留） |

- **项目必须先 `PUBLISHED`（§7），任务才能引用它**；草稿 / 下架项目会直接报错。
- **任务不等于可见性**：项目 `PUBLISHED` 就对全体学生开放（能看能做）；任务只决定"哪些项目是必修"（§9.2）。
- **定时发布靠宿主的 cron 驱动**（`scripts/dispatch_publish_tasks.py`）：脚本不跑，到点的任务不会自己生效，也不做"查询时顺便判定"的双口径。
- **撤回不能重发**：`CANCELLED` 的任务不能再 publish，要重新发就**新建一条**。

### 8.2 创建并下发任务

`POST /api/publish-tasks` → **201**

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| title | string(150) | 是 | 任务名称 |
| description | string | 否 | 任务说明（学生端展示） |
| project_level | string(20) | 否 | `BASIC` / `ADVANCED` / `EXPANDED`；留空不限层级 |
| job_ids | int[] | 否 | **岗位范围，只用于筛项目，不筛学生**；留空 = 全部岗位 |
| targets | array | 是 | 目标班级 / 分组，至少 1 个 |
| project_ids | int[] | 否 | 手工指定项目；**留空 = 按「岗位 × 层级」自动把符合条件的已发布项目全带上** |
| publish_mode | string(20) | 否 | `IMMEDIATE`（默认，创建即生效）/ `SCHEDULED` |
| scheduled_at | datetime | 否 | 定时发布时间；`SCHEDULED` 必填，且必须晚于当前时间 |
| deadline_at | datetime | 否 | 截止时间；必须晚于当前时间 |
| creator_id | int | 否 | 发布教师 ID（接登录后从登录态取） |
| remark | string(255) | 否 | 备注（仅教师可见） |

`targets[]` 每一项：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| class_id | int | 是 | 目标班级 ID |
| target_type | string(20) | 否 | `CLASS`（默认，全班）/ `GROUP`（指定分组） |
| group_id | int | 否 | `target_type=GROUP` 时必填；`CLASS` 时不能传 |

```bash
curl -X POST $BASE/publish-tasks -H 'Content-Type: application/json' -d '{
  "title": "第 3 周 · 基础实训",
  "description": "完成 1 个基础项目，提交实训报告",
```

### 8.6 修改 / 立即发布 / 撤回 / 删除

| 操作 | 接口 | 说明 |
| --- | --- | --- |
| 修改 | `PATCH /api/publish-tasks/{task_id}` | 未发布可全量改；**已发布只能改 `description` / `deadline_at` / `remark`** |
| 立即发布 | `POST /api/publish-tasks/{task_id}/publish` | 定时任务也可以提前发；`creator_id` 作为 query 参数传，用于记审计操作人 |
| 撤回 | `POST /api/publish-tasks/{task_id}/cancel` | 必修标记立刻消失（项目本身照旧开放），已产生的闯关记录保留；给学生的通知里说明"已完成的部分会保留" |
| 删除 | `DELETE /api/publish-tasks/{task_id}` | 软删，**只能删从没发布过的任务**；同时清掉目标 / 岗位 / 项目关联 |

已发布任务的锁定提示：

```bash
curl -X PATCH $BASE/publish-tasks/1 -H 'Content-Type: application/json' -d '{"title":"改标题"}'
```

```json
{"code": 422, "msg": "任务已发布或已撤回，目标 / 项目 / 岗位 / 层次已锁定；要改请撤回后新建一条任务", "data": null}
```

其余状态类错误：

| 场景 | `msg` |
| --- | --- |
| 重复发布 | `任务已经发布，不用重复发布` |
| 撤回后再发布 | `任务已撤回，不能重新发布；请新建一条任务` |
| 删除发布过的任务 | `任务已经发布过，不能删除；请先撤回，记录会保留在平台上` |
| 发布时项目已被下架 / 改回草稿 | `《缺陷检测实训》不在已发布状态，不能发布任务；请先发布或撤回这些项目` |
| 任务里项目全被剔除 | `任务里已经没有可发布的项目` |

> ⚠️ **已知问题：PATCH 改「目标 / 岗位 / 项目」目前不可用**（2026-09-16 实测）。
> - 传 `targets` → `code=500`（内部把对象当字典取属性，抛 `'dict' object has no attribute 'target_type'`）；
> - 只传 `project_level` / `job_ids` / `project_ids` → `code=422`、`msg="请至少选择一个目标班级"`（改这几项的内部逻辑要求同时传 `targets`）。
>
> 所以当前**改目标 / 项目 / 岗位 / 层级只能「撤回 + 新建」**；`PATCH` 请只用于 `description` / `deadline_at` / `remark`，以及 `PENDING` 任务的 `title` / `publish_mode` / `scheduled_at`（这几个实测正常）。

```json
      ]
    }
  ]
```

任务"点名"（必修）口径 —— 判定谁被这条任务要求完成这些项目：

1. 班级目标命中该学生的**在班记录**（`class_student.status='ENROLLED'`）即命中；
2. 分组目标按**当前分组**实时判定，老师把学生调走，他立刻不再被这个分组任务点名；
3. 同一条任务命中多个目标（比如两个班都发了）**只出现一次**，项目按项目去重；
4. 必修只是标记：项目本身 `PUBLISHED` 就对所有学生开放，学生没被点名也能做；
5. 学生做过的项目，**进度跟着"学生 × 项目"走**，换班、换任务、换老师都不会丢（见 §4.3.2）；
6. 撤回 / 删班后必修标记消失，但 `student_project`、提交与评审记录都还在库里。

### 8.8 任务下发常见坑

1. **任务只标必修，不决定可见性**：项目 `PUBLISHED` 后学生端立刻能看到并闯关；发任务只是把项目标成"老师点名要求完成"（`is_required=true`），方便教师端统计完成率。
2. **定时发布依赖 cron**：`scripts/dispatch_publish_tasks.py` 没跑，`PENDING` 会一直挂着；脚本会复核项目状态，被下架的项目从任务里剔除，剔除空了就整体留在 `PENDING` 并记 `SKIP` 审计。
3. **`project_ids` 留空 ≠ 不发项目**：会按「岗位范围 × 层级」自动把符合条件的已发布项目全带上，容易多发，前端建议显式传 `project_ids`。
4. **`job_ids` 不筛学生**：它只影响"自动挑哪些项目"，不会改变覆盖的班级 / 分组。
5. **任务进度看板**（§5）里 `PENDING` / `CANCELLED` 任务也会出现，靠 `effective` 字段区分；只有 `PUBLISHED` 的完成率进平均。
6. **撤回是单向的**：撤回不可逆，重新发布请新建任务；这条设计是为了让"发过什么"有据可查。

## 9. 闯关评审：记录 / 轮次 / 作答 / 提交 / 评审 / 文件台账

对应实现：`app/api/endpoints/attempts.py`、`app/api/endpoints/reviews.py`、`app/services/attempt.py`、`app/services/ai_review.py`。共 38 个接口，是学生端主流程所在。

### 9.1 四张表与状态流转

| 层 | 表 | 一个学生做一次项目 → |
| --- | --- | --- |
| 实训记录 | `student_project` | **1 条**（学生 × 项目）：`NOT_STARTED → IN_PROGRESS → SUBMITTED → COMPLETED` |
| 闯关轮次 | `training_attempt` | **每挑战一次 1 条**：`IN_PROGRESS → SUBMITTED → COMPLETED`（放弃是 `ABANDONED`） |
| 关卡作答 | `attempt_stage` | 每轮里每个关卡 **1 行**（开始闯关时自动建好，逐关填 `answer_text`） |
| 整单提交 | `project_submission` | 每轮可提交多次：`PENDING_AI → AI_PASSED / AI_FAILED →（教师复审）REVIEWED`，学生可 `WITHDRAWN` |

「重新挑战」= 再调一次 `start`，会新建一轮 `training_attempt` 与整套 `attempt_stage`，**上一轮的作答与分数保留**；实训记录的 `best_score` 只升不降。

| POST | `/api/students/{student_id}/my-projects` | 批量加入（body `{"project_ids":[1,2]}`）；全是新加 → **201**，一条都没新增（全重复）→ **200** |

| DELETE | `/api/students/{student_id}/my-projects/{project_id}` | 移出；不在清单里也算成功（幂等） |

口径：

1. **清单表只存"学生主动挑的"**（`student_project_pick`）；老师发任务点名（必修）**不写表**，展示时实时并集 —— 所以任务撤回、转班、删班都不需要同步清单；
2. 一条项目在列表里只有一条，用两个标记说明"为什么在这里"：`picked`（自己加的）、`is_required`（老师点名），另有派生字段 `sources`（`SELF` / `TEACHER`，可能同时存在）；
3. **必修移出后仍在列表里**（必修是任务算的），删除接口的 `message` 会提示；任务撤回后它才真正消失。自己挑过的项目，任务撤回后仍留在清单里；
4. **排序**：必修置顶 → 学生自定义 `sort_no` → 加入时间新的在前。没排过的项目按加入时间倒序，`PATCH .../order` 写入 1..N；
5. **项目下架 / 删除**后不再出现在列表里，但清单记录保留（项目重新上架自动回来）；列表只包含 `PUBLISHED` 的项目；
6. **加入清单不影响技能进度**：技能分母仍是"该技能点关联的全部已发布项目"（`app/services/skill.py`）。

```json

  "msg": "ok",
  "data": {
    "id": 1,
    "submission_id": 1,
    "review_kind": "TEACHER",
    "version_no": 1,
    "status": "FINAL",
    "reviewer_id": 2,
    "total_score": "88.00",
    "conclusion": "PASS",
    "comment": "整体不错",
    "dimension_json": [{"name": "需求分析", "score": "9", "weight": "10", "reason": "描述清晰"}],
    "ai_model": null,
    "raw_json": {},
    "finished_at": "2026-09-16T10:15:00",
    "created_at": "2026-09-16T10:15:00"
  }
}
```

**定稿（`status=FINAL`）是唯一的结算触发点**，一次定稿会做四件事：

1. 按**项目层级的及格线**判 `conclusion`（`total_score >= pass_score` → `PASS`，否则 `FAIL`；结论不由评审人手填）；
2. 提交记录写上 `final_conclusion` / `reviewed_at`，状态转 `REVIEWED`；
3. `PASS` 时把学生实训记录置 `COMPLETED`、写 `completed_at` / `completed_score`，并更新 `best_score`（只升不降）；
4. 重算该项目关联的**全部技能节点进度**（§6.5）。

实测：定稿 88 分后，`GET /student-projects/1` 变成 `status=COMPLETED`、`progress=100.00`、`best_score=88.00`；`GET /students/2/skills` 里该技能点 `progress=100.00`、`source=PROJECT`、`mastered_at` 有值。

其余限制：

| 场景 | 返回 |
| --- | --- |
| 定稿没给分 | `code=422`、`msg="定稿必须给出分数，系统按项目层级的及格线判定是否通过"` |
| 已定稿又改回草稿 | `code=422`、`msg="已定稿的评审不能再改回草稿"` |
| 删除已定稿的评审 | `code=422`、`msg="已定稿的评审不能删除"` |
| `dimension_json` 缺 `name` | `code=422`、`data` 指出 `body.dimension_json.0.name` 必填 |

### 9.7 AI 评审

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/submissions/{submission_id}/ai-review` | **同步跑一次完整 AI 评审** → **201** |
| GET | `/api/submissions/{submission_id}/ai-jobs` | AI 评审任务列表 |
| POST | `/api/submissions/{submission_id}/ai-jobs` | 重新排一次 AI 评审任务 → **201** |
| PATCH | `/api/ai-jobs/{job_id}` | 回写任务状态（真实调用由异步 worker 负责） |

`POST /api/submissions/{id}/ai-review` 的链路是 **RAG 召回本项目的评分标准 → 大模型打分 → 落库并结算**：

```json
{
  "code": 200,
  "msg": "ok",
  "data": {
    "review": {"id": 2, "submission_id": 1, "review_kind": "AI", "status": "FINAL", "total_score": "82.00", "conclusion": "PASS", "ai_model": "DeepSeek V4 Pro", "dimension_json": [], "raw_json": {}, "created_at": "2026-09-16T10:20:00"},
    "criteria_doc_ids": [7],
    "recalled_chunks": 6,
    "model": "DeepSeek V4 Pro",
    "warnings": []
  }
}
```

要点与坑：

1. **评分标准只在校内链路检索**（`doc_type=EVAL_CRITERIA`），学生端没有任何入口能读到；评分标准靠「项目附件 + `SCORING_CRITERIA`」上传（§7.5）。
2. **这个接口是同步的**：在请求内跑完"召回 + 打分"，约几秒；并发上来后应改成消费 `review_ai_job` 的后台任务。
3. 模型、api key、检索参数都来自 `system_config`（`review.ai` / `ai.llm` / `rag.retrieval`），换模型不用改代码。
4. 没配模型 / 没装向量依赖时，`warnings` 会说明降级原因；召回不到评分标准时按通用标准打分。
5. `ai-jobs` 三个接口是"任务台账"，用于异步化与对账：`job_status` = `QUEUED` / `PROCESSING` / `SUCCEED` / `FAILED`，`attempt_count` 记重试次数。

### 9.10 闯关评审常见坑

1. **`start` 会新建一轮**：不要用它在页面刷新时"确保有轮次"，前端应先读详情里的 `current_attempt_id`。
2. **批量保存的键是 `attempt_stage_id`**；单关保存路径里的 `{stage_id}` 与它是同一个 ID。
3. **只有 `FINAL` 评审会结算**：草稿评审（`DRAFT`）不改提交状态、不改项目完成、不动技能。
4. **结论不是评审人填的**：后端按项目层级 `pass_score` 判 `PASS` / `FAIL`，前端别自己写死 60。
5. **AI 评审是同步调用**：超时 / 降级看 `warnings`，别在前端做长轮询等它。
6. **一个学生同一项目可以反复挑战**：`best_score` 取历史最高；首次通过后 `completed_at` 不会因为再挑战而清除。

切片项字段：`chunk_index` / `content` / `char_count` / `heading_path`（引用展示用）/ `page_no` / `token_count` / `vector_id` / `model_name` / `status`（`PENDING` 已切片待入库 / `READY` 已写入 Milvus / `FAILED` / `DISABLED`）。

**文档没有"直接创建"接口**：`KNOWLEDGE` 类文档走知识入库流程，`EVAL_CRITERIA` 类从项目附件上传时自动入库（§7.5 的 `SCORING_CRITERIA`）。删除时顺序固定为 **Milvus 向量 → 切片 → 文档**，Milvus 挂了会在 `msg` 里带告警，而不是留下"搜得到又回溯不了"的脏命中：

```json
{"code": 200, "msg": "ok", "data": {"success": true, "message": "知识文档 7 已删除，连带删除 18 条切片，Milvus 向量已清理"}}
```

### 10.2 重新切片与向量化

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/knowledge/docs/{doc_id}/reparse` | 重新切片（幂等重建，改了切分参数后用） |
| POST | `/api/knowledge/docs/{doc_id}/embed` | 向量化并写入 Milvus（切片推进到 `READY`） |

```json
{"code": 200, "msg": "ok", "data": {"knowledge_doc_id": 7, "doc_type": "EVAL_CRITERIA", "status": "READY", "chunk_count": 18, "chunk_strategy": "by-heading-v1", "parse_error": null, "warnings": []}}
```

```json
{"code": 200, "msg": "ok", "data": {"knowledge_doc_id": 7, "chunk_count": 18, "collection": "knowledge_chunk_v1", "model": "BAAI/bge-m3", "truncated": 0}}
```

要点：`reparse` 只重切片（不重建向量），改完切片要再 `embed`；`embed` 增量写 Milvus，**集合物理名 = `rag.vector_store.collection_alias` + `collection_version`（默认 `knowledge_chunk_v1`）**，对外查询用别名 `knowledge_chunk`。换 embedding 模型时要同步升 `collection_version`（或换 alias），否则新旧模型的向量会混在同一个集合里检索。

### 10.3 召回测试

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/knowledge/docs/{doc_id}/recall` | 单文档召回测试 |
| POST | `/api/knowledge/recall` | 跨文档召回（可用 query 参数 `project_id` / `doc_type` 限定，**AI 评审走的就是这条**） |

入参 `{"query":"缺陷检测的评分标准是什么","top_k":5,"use_rerank":false}`：

```json
{
  "code": 200,
  "msg": "ok",
  "data": {
    "query": "缺陷检测的评分标准是什么",
    "doc_ids": [7],
    "candidate_count": 12,
    "reranked": false,
    "warnings": [],
    "hits": [
      {
        "chunk_id": 33,
        "doc_id": 7,
        "chunk_index": 4,
        "heading_path": "二、评分细则 > 2.1 缺陷识别",
        "content": "缺陷识别部分占 20 分，要求……",
        "score": 0.72,
        "rerank_score": null
      }
    ]
  }
}
```

要点与坑：

1. **需要 Milvus 与向量模型可用**；没装 `pymilvus` 或连不上库时接口会报 `code=500`，先用 `GET /api/health/milvus` 排查。
2. `rag.retrieval.score_threshold` 目前**只是配置项、还没生效**；`use_rerank=true` 需要装重排依赖，缺失时 `warnings` 会提示并降级。
3. 该项目下没有已入库文档时不报错，返回 `warnings=["该项目下没有已入库的知识文档"]`、`hits=[]`。
4. **评分标准（`EVAL_CRITERIA`）没有对外问答入口**：学生端任何接口都检索不到它，只能被 AI 评审在服务端内部调用。

## 11. AI 问答：会话 / 提问（SSE）/ 用量

对应实现：`app/api/endpoints/qa.py`、`app/services/qa.py`。**一期不接检索**：回答来自大模型通用知识，`citations` 恒为空数组，`warnings` 里明确写"未接入知识库检索"。

### 11.1 会话

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/qa/sessions` | 新建会话 → **201** |
| GET | `/api/qa/sessions` | 我的会话列表（`student_id` 必传，`status` 可筛） |
| GET | `/api/qa/sessions/{session_id}` | 会话详情（默认带最近 30 条消息，`message_limit` 1~200） |

| PATCH | `/api/qa/sessions/{session_id}` | 改名 / 关闭 / 重开 |
| DELETE | `/api/qa/sessions/{session_id}` | 删除会话（连带消息与引用） |

```bash
curl -X POST $BASE/qa/sessions -H 'Content-Type: application/json' \
  -d '{"student_id":2,"title":"实训答疑","subject":"工业视觉"}'
curl "$BASE/qa/sessions?student_id=2&status=ACTIVE"
curl "$BASE/qa/sessions/1?student_id=2&message_limit=30"
```

```json
{
  "code": 200,
  "msg": "ok",
  "data": {
    "id": 1,
    "student_id": 2,
    "title": "实训答疑",
    "subject": "工业视觉",
    "status": "ACTIVE",
    "created_at": "2026-09-16T10:30:00",
    "updated_at": "2026-09-16T10:30:00",
    "messages": []
  }
}
```

会话接口除新建外**每个都要带 `student_id`（query 参数）**做归属校验：会话不属于该学生、或超出保留期（默认 7 天，来自 `qa.limits.retention_days`）时统一返回 `code=422`、`msg="问答会话 1 不存在"` / `msg="该会话已超出保留期（仅保留最近 7 天），请新建会话"` —— 越权与过期不区分，避免泄露会话是否存在。

消息翻页用**游标**（`next_before_id`）而不是 offset，因为流式回答是逐轮追加写入的：

```json
  "msg": "ok",

    ],
    "total": 24,
    "next_before_id": 1
  }
}
```

### 11.2 提问（默认 SSE 流式）

`POST /api/qa/sessions/{session_id}/ask`，入参：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| student_id | int | 是 | 学生 ID（SSO 落地后改由登录态覆盖） |
| question | string | 是 | 本轮问题 |
| stream | bool | 否 | `true`（默认）走 SSE 流式；`false` 返回一次性 JSON |
| model | string | 否 | 模型选项 id（`deepseek` / `kimi` / `mimo`…，与 `ai.llm.models` 的键一致）；留空用默认模型。该家没配 api_key / 地址时返回 422 与可读原因 |

```bash
# 流式（默认）
curl -N -X POST $BASE/qa/sessions/1/ask -H 'Content-Type: application/json' \
  -d '{"student_id":2,"question":"缺陷检测怎么入手？"}'

# 一次性 JSON
curl -X POST $BASE/qa/sessions/1/ask -H 'Content-Type: application/json' \
  -d '{"student_id":2,"question":"缺陷检测怎么入手？","stream":false}'
```

非流式返回（带统一响应体）：

```json
{
  "code": 200,
  "msg": "ok",
  "data": {
    "message": {"id": 2, "session_id": 1, "role": "ASSISTANT", "content": "建议先明确检测对象……", "model_name": "Kimi 2.6", "prompt_tokens": 820, "completion_tokens": 210, "status": "COMPLETED", "created_at": "2026-09-16T10:31:05"},
    "usage": {"prompt_tokens": 820, "completion_tokens": 210, "estimated": false},
    "citations": [],
    "warnings": ["当前未接入知识库检索，回答来自大模型通用知识"],
    "elapsed_ms": 3120
  }
}
```

两条硬约定：

1. **SSE 不走统一响应体信封**（`text/event-stream` 被原样放过），流中途的错误只能用 `error` 事件表达，不能指望全局兜底；响应头带 `Cache-Control: no-cache` 与 `X-Accel-Buffering: no`，否则反向代理会把流攒成一坨再吐。
2. 生成器**一开写就先发 `meta` 事件**（前端拿落库的消息 id），后续 `done` 才能与库里的记录对上。

### 11.3 用量统计

`GET /api/qa/usage?student_id=2` → 当日与保留期内的 token 用量（**只统计不限制**）：

```json
{
  "code": 200,
  "msg": "ok",
  "data": {
    "student_id": 2,
    "retention_days": 7,
    "today": {"scope": "today", "question_count": 2, "prompt_tokens": 820, "completion_tokens": 210, "total_tokens": 1030},
    "recent": {"scope": "recent_7d", "question_count": 17, "prompt_tokens": 5240, "completion_tokens": 1330, "total_tokens": 6570}
  }
}
```

`citations` 一期恒为空数组；`message.status` 为 `COMPLETED` / `FAILED`；token 数在端点没返回 usage 时会按字符估算，并把 `usage.estimated` 置 `true`。

## 13. 注意事项与常见坑

1. **导入是整批事务**：一行不合法整批不落库（含"学号已存在"），前端要先把 `data` 里的逐行原因展示出来再让老师重传；只是补录已有账号请用单个加人接口。
2. **`group_count` 不会自动建组**：建班时填的数量只用于展示，分组要显式调 §4.6.1。
3. **重新分组用的是 `class_student_id`**（在班记录 ID），不是 `student_id`；学生转出再入班会生成新的在班记录。
4. **重新分组只影响"必修名单"**：分组目标的任务按当前分组实时算，把人调走，他就不再算在那个任务的必修名单里（闯关记录保留）；技能进度的分母是"全部已发布项目"，与班级 / 分组 / 任务都无关，所以入班、换组、离班都不会让进度变化。
5. **删除班级是软删**，且不会删学生；删掉之后发给该班的任务不再点名这些学生（项目照旧能看能做）。
6. **换负责教师**（`PATCH /classes/{id}` 的 `head_teacher_id`）会直接改变 §5 教师看板能看到的班级范围（学生端的项目可见性不受影响）。
7. **任务进度与技能进度同源**：都看 `student_project.completed_at`（评审通过且达到及格线），不是"提交了就算完成"。
8. **鉴权尚未实现**：现在任何人传别人的 `teacher_id` 都能看到那个老师的班级；上鉴权后要从登录态取用户，而不是信任 URL 里的 ID。
9. **一个学生可以同时在多个班（甚至多个老师的班）**：必修取并集 —— 每条点名他的任务都会出现在"我的任务"里，同一条任务命中多个目标（例如两个班都发了）也只出现一次、只发一条通知；项目按项目去重，所以**技能进度的分母是"全部已发布项目数"，不会因为同一项目被发过两次而翻倍**。教师的班级看板只看得到自己的班，跨班学生会在每个班里各算一次（`student_count` 跨班不去重）。
10. **两个"发布"要分清楚**：项目的 `PUBLISHED` = **对学生开放**（学生端立刻能看能做）；任务的 `PUBLISHED` = **点名必修**（`is_required=true`，教师看板按它统计完成率）。任务不改变可见性（§7.1、§8.1）。
11. **权重合计必须是 100 才能发项目**：`POST /api/projects/{id}/modules` 加完关卡后，用项目详情看 `weight_total`，不等于 100 就逐关卡 `PATCH weight`；校验不过时接口返回 `422`，**项目状态不会变**。
12. **模块库是关卡的唯一来源**：项目里加不了"临时关卡"；被项目选中的模块删不掉（先移除再删）。同名模块重新新增会**恢复原来那条记录**（HTTP 200、`id` 不变）。
13. **附件不是关卡附件**：项目附件（报告模板 / 数据集 / 评分标准）是给整个项目用的；学生每个关卡的作答附件走 `/api/attempts/*`。
14. **Decimal 字段是字符串**：`weight` / `default_weight` / `weight_total` / 分数等在 JSON 里是 `"20.00"` 这样的字符串，前端要 `parseFloat` 后再参与计算。
15. **`PATCH /api/publish-tasks/{id}` 改目标 / 项目 / 岗位 / 层级目前不可用**（传 `targets` 会 500，只传 `project_ids` 会报"请至少选择一个目标班级"）：要改这些字段，撤回任务后新建一条；`PATCH` 只用于 `description` / `deadline_at` / `remark`（详见 §8.6）。
16. **`job_id`（项目绑定岗位）后端不做存在性校验**：传了不存在的岗位 ID 会触发外键错误（500），前端务必从 `/api/jobs` 列表里取值。
17. **状态码与文案统一从 `/api/enums` 取**：枚举键 30 个，别在前后端各写一份中文映射（§2.2）。
18. **密码只在两处出现**：`POST /api/users`（写默认密码哈希）与两个重置接口；任何返回都不含密码字段。默认密码是 `settings.default_password`（默认 `123456`），上线前必须改（§3.1）。
19. **角色的「覆盖式」语义**：`POST /roles/{id}/permissions`、`POST /users/{id}/roles`、`PUT /projects/{id}/skills`、`PUT /jobs/{id}/skills`、`PUT /skill-nodes/{id}/dependencies` 都是**先清空再写入**，传空数组即清空，不要当成"追加"（§3.2、§6.1）。
20. **删除有引用保护的四处**：删角色（还挂在用户上）、删权限点（还挂在角色上）、删模块库条目（还被项目选中）、删分组（组里还有人）会直接 `code=422`，要按提示先解除关联（§3.2、§7.2、§4.6）。
21. **系统配置是整体替换**：`config_value` 更新时不会深合并，改一项前先 GET 出来改好再 PATCH 回去；改 `ai.embedding.version` 会换 Milvus 集合，属于"重建向量库"级别操作（§3.3、§10.2）。
22. **AI 相关接口依赖外部服务**：AI 评审（`/submissions/{id}/ai-review`）需要 `ai.llm` 配置可用，AI 问答（`/qa/sessions/{id}/ask`）需要 `qa.limits` 指向的模型可用，知识库召回需要 Milvus + BGE-M3。这些接口在开发机上可能直接报错，先用 `/api/health/milvus` 与 `system-configs` 排查（§9.7、§10、§11）。
23. **上传附件依赖对象存储（S3 / MinIO）**：测试前先 `docker compose -f deploy/docker-compose.rag.yml up -d`，否则项目附件与作答附件都会 500（§9.8）。
24. **教师后手改成绩不会自动重算技能**：`PATCH /api/student-projects/{id}` 只改记录，要同步技能请再调 `POST /api/students/{id}/skills/recalculate`（§9.9）。
25. **`DELETE /api/student-projects/{id}` 是物理删除**（连带轮次、作答、提交），与其它域的软删不同，前端必须二次确认（§9.9）。
26. **列表接口的默认过滤要看清楚**：`GET /api/classes/{id}/students` 与 `GET /api/groups/{id}/students` 默认只返回 `ENROLLED`，要看离班学生得显式传 `status=LEFT`（§4.6.2）。
